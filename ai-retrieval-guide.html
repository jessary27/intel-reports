Part 1

Six Retrieval Paradigms

Each method operates on a fundamentally different retrieval mechanism. The choice has architectural consequences that compound at scale.

⚠️

Architectural Warning

Choosing the wrong retrieval architecture is not a tuning problem — it is an architectural mismatch. Vector similarity and graph traversal answer fundamentally different questions. Getting the choice wrong costs months of engineering time.

🔤
Sparse / BM25
Term-frequency lexical matching
FastLatency
LowCost
MediumAccuracy

Scores documents on TF-IDF statistics. No embeddings, no GPU. Deterministic and interpretable. Outperforms semantic search ~30% of the time on technical documentation with exact terminology.

Exact keywords Named entities Deterministic No synonyms No multi-hop

Semantic bi-encoder embedding matching
FastLatency
MediumCost
GoodAccuracy

Encodes text into high-dimensional vectors. Retrieves semantically similar documents even with varied phrasing. Leading vector DBs achieve ~93% recall at 100M vector scale. Chunk size is critical: 256-token chunks with 64-token overlap outperform most alternatives.

Semantic matching Paraphrase handling OOD domain risk No relational reasoning

BM25 + Dense + Cross-encoder
MediumLatency
MediumCost
BestAccuracy

Stage 1: fuse BM25 + dense retrieval via Reciprocal Rank Fusion (top 20). Stage 2: cross-encoder reranker scores full [query, doc] pairs → top 5. Improves Context Precision 15–30%. Reduces hallucination rates from 31.7% to 18.3% vs. post-filtering.

Default enterprise architecture Best precision+recall Engineering complexity

Best for small static corpora under 500 pages.

Part 3

Evaluation Framework

Retrieval quality measurement requires both quantitative metrics and end-to-end RAG evaluation. RAGAS provides the dominant automated framework.

Core Retrieval Metrics

🎯
Recall@K
|relevant ∩ top_K| / |relevant|

Most critical production metric. Measures what fraction of truly relevant documents appear in top K results. Below 80% recall, hallucination rates spike significantly. Optimize first.

📌
Precision@K
|relevant ∩ top_K| / K

Fraction of top-K results that are actually relevant. Optimized when irrelevant results harm UX. High precision reduces hallucination from stale context injection.

🥇
MRR
mean(1 / rank_of_first_relevant)

Mean Reciprocal Rank. Focuses on where the first correct result appears. Common in QA systems where users read only top results.

📊
NDCG@K
DCG@K / IDCG@K

Normalized Discounted Cumulative Gain. Handles graded relevance. Discounts results by position. Used when ranking order matters, not just presence.

✅
Hit Rate
1 if any relevant in top_K else 0

Binary: did retrieval surface at least one relevant result? Useful for simple found/not-found evaluation. Misses ranking quality.

🗺️
MAP
mean(avg precision per query)

Mean Average Precision. Holistic benchmark comparison metric — used by BEIR and TREC. Expensive to compute but definitive for cross-system comparisons.

RAGAS End-to-End Evaluation

RAGAS Dimension What It Measures Formula Target Score If Low → Fix
Faithfulness Are all response claims supported by retrieved context? supported claims / total claims > 0.85 Prompt constraints; stronger model
Answer Relevance Does the answer actually address the query? LLM-scored relevance 0–1 > 0.80 Query reformulation; prompt engineering
Context Recall Did retrieval surface the right documents? attributed sentences / ground truth sentences > 0.80 Improve chunking; add hybrid search
Context Precision Was retrieved context free of irrelevant content? useful chunks / total chunks retrieved > 0.70 Add reranker; reduce K; tighten filters
🔬

Hallucination Priority Stack

Fix retrieval first. Retrieval failures are the most common cause — and the highest-ROI fix. Then: constrain generation → add citations → verify outputs → route to human review. Naive implementations produce 15–25% hallucination rates; well-engineered systems reduce this to under 3%.

Part 8

Key Takeaways

The ten findings that should inform every retrieval architecture decision.

1

Measure retrieval first. Context Recall below 80% is the dominant failure mode — it drives hallucination regardless of how good your generation model is. Fix retrieval before optimizing generation.

2

Hybrid + cross-encoder is the default production architecture. BM25 + Dense + reranker balances precision, recall, and latency across heterogeneous enterprise corpora. This is the proven starting point.

3

Long context windows are not a replacement for RAG. 1,250× more expensive, 30–60s latency at 1M tokens, effective capacity is 60–70% of advertised limits, and accuracy degrades with "lost in the middle" for centrally-positioned content.

4

GraphRAG's advantage is query-type conditional. It triples enterprise accuracy for structural/multi-hop queries but underperforms standard RAG on single-hop detail-heavy tasks. Justify the build cost with a query distribution audit.

5

RAG consistently beats fine-tuning for new knowledge. RAG doubled accuracy over supervised fine-tuning in 2026 multi-hop benchmarks. Fine-tune behavior and style; use RAG for facts and freshness.

6

Chunking is the highest-ROI optimization. 256-token chunks with 64-token overlap outperform most alternatives. This is cheaper and faster to tune than switching embedding models or adding pipeline stages.

7

Token efficiency drives long-term cost. Pre-structured compact knowledge graphs use 11× fewer tokens per query at 4× higher accuracy on structured domains. The architecture choice directly determines your inference bill at scale.

8

Agentic RAG is proven but expensive. Reserve for complex synthesis tasks where static RAG demonstrably fails. Products like Perplexity, Harvey AI, and Glean have productionized this at scale, so the pattern is viable — but latency and cost are real constraints.

9

Evaluate with RAGAS on four dimensions. Faithfulness, Answer Relevance, Context Recall, Context Precision — not just end-user accuracy scores. Each dimension diagnoses a different failure mode and points to a different fix.

10

No single method wins everything. The optimal system is a hybrid tuned to query distribution and cost constraints. RAG and GraphRAG are complementary — 13.6% of queries are exclusively answered by GraphRAG; 11.6% are exclusively answered by RAG on MultiHop-RAG benchmarks.
